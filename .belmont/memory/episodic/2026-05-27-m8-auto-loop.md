# 2026-05-27 — M8 auto mode (two-runtime, sequential) + lifecycle ownership + 10-iter leak test

## What happened

- **Two-runtime split, sequential per task** (§7.1 + §7.3). Runtime A
  is the user's REPL (`ExtensionCommandContext` in command handlers);
  Runtime B is the worker — built once per `/belmont:auto` invocation
  via `createBelmontWorker` (in `packages/harness/src/pi/worker.ts`),
  with per-phase `runtime.newSession({model, thinkingLevel})` calls
  flipping the impl-tier vs verify-tier without disturbing Runtime A.
  No worktrees, no IPC, no `__worker` framing — one in-process
  `AgentSessionRuntime` per auto run.
- **BelmontWorkerHandle as the §8.2 hard API boundary.** Only
  `pi/sdk.ts` (re-exports) and `pi/worker.ts` (the worker construction)
  hold raw `AgentSessionRuntime` / `AgentSession` / `MessageRenderer`
  objects. The handle exposes exactly `newSession`, `promptCurrent`,
  `abortCurrent`, `subscribe`, `currentSessionId`, `dispose`,
  `diagnostics`. The handle ALSO surfaces a Belmont-shaped event union
  (`WorkerEvent`: phase_start/phase_end/text/tool_call/tool_result/abort)
  so the auto loop's renderer hook never sees pi types directly. Pi-
  boundary lint + dep-cruiser path rules confirm the boundary holds.
- **Disposal discipline asserted twice.** First the wrapper-internal
  ordering (`unsubscribeCurrent()` BEFORE `runtime.newSession()` so
  the §8.4 invariant "after.listeners === before.listeners" holds in
  the 10-iter test); second the §8.5 AST-walk lint in
  `test/dispose-finally.test.ts` that fails if any `createBelmontWorker`
  callsite lacks a paired `finally{…dispose()…}` (the regex matches
  the file-level pattern; the loop callsite is the v1.0 ONLY callsite
  and is explicitly pinned in the second assertion).
- **The §8.4 leak-test introspection-path call (ultrathink).** Verified
  ABSENT at `node_modules/@earendil-works/pi-coding-agent@0.75.5/dist/
  core/{agent-session,agent-session-runtime,session-manager}.d.ts` —
  pi exposes only public getters (`session`, `services`, `diagnostics`)
  + public methods (`newSession`, `dispose`, etc.); no
  `_internal.activeResources` accessor. Picked path (b) per §8.4 last
  paragraph: `process._getActiveHandles()` + `_getActiveRequests()`
  snapshot before vs after 10 iterations × {newSession × 2 +
  promptCurrent × 2 + dispose}, with ±2 slack for vitest scheduling
  jitter. The leak test ALSO asserts the wrapper-internal contract:
  `runtimesCreated === runtimesDisposed`, `sessionsCreated ===
  sessionsDisposed`, `subscribersInstalled === subscribersUnsubscribed`.
  File header documents the gap + cites the §8.4 fallback explicitly.
- **The decide ladder** is in `auto/decide.ts` — pure rules (consume
  steer → plan/done/triage/continue/verify/implement → stuck) AND an
  optional AI fallback via the existing worker (no extra pi entry
  point — the fallback `worker.newSession({tier: "next"})` runs
  through the same handle that's already in the loop's finally). Tests
  cover all 7 rule branches + the AI-fallback wrapper's three paths
  (rules pass → use rules; rules stuck + AI returns valid → use AI;
  rules stuck + AI returns invalid → stay stuck).
- **Steering consume-before-invoke** (§7.2, D-008). `auto/steering.ts`
  exposes `consumeSteeringFile(cwd)` — reads + unlinks
  `.belmont/memory/steering/steering.md` in one go, returns trimmed
  body or `undefined`. The loop calls this at the TOP of each
  iteration; `decideRules` short-circuits to `consume_steer` if the
  body is present (so the next sub-session prompt-build picks it up
  before any pi LLM call fires). Replace-not-append semantic preserved:
  `/belmont:steer "X"` then `/belmont:steer "Y"` leaves only Y.
- **Watchdog (§7.5)** composes via `AbortController` + setInterval. 5
  min hard ceiling per phase, 30s no-output abort (resets on every
  text/tool event from the worker's `subscribe()`), both feeding
  `worker.abortCurrent()`. The phase outcome (`{outcome: "ok" |
  "failed" | "aborted", message?, lastAssistantText}`) flows back to
  the loop, which writes the failure into the episodic event +
  transitions stay at `done` (never `verified`) on aborted verify
  phases.
- **Worker → Runtime A stream pipe.** `pi.registerMessageRenderer(
  "belmont.worker", …)` in `auto/render.ts` registers a custom
  renderer; the loop's worker-event hook converts `WorkerEvent`s into
  `pi.sendMessage({customType: "belmont.worker", …})` calls. User
  opted into streaming every `text_delta`, but v1.0 batches at
  message_end (the `partial` flag in `WorkerEvent.text` discriminates)
  to avoid hammering Runtime A's scroll buffer with 1000 partial
  messages per turn — no deltas are dropped, just batched at the
  natural message boundary. Tool-call events emit; tool-result events
  emit ONLY when `isError === true` (de-noise default).
- **Singleton control plane** for `/belmont:steer` /stop /pause /resume.
  `auto/loop.ts` holds the `activeAuto` module-state (start when
  `runAuto` is called, clear in its `finally`). Commands in
  `commands/auto.ts` get the singleton via `getActiveAuto()` and flip
  flags (`paused`, `stopRequested`); the loop polls these between
  iterations. `/belmont:stop` ALSO writes `.belmont/auto.stop` so a
  crashed loop can re-detect on next launch. `/belmont:steer` writes
  the steering file then returns — no IPC, no signal, just FS that
  the loop reads next iteration.
- **`.belmont/auto.json` runtime ledger** (§4.3) atomic-writes via

  stopRequested, workerSessionId, startedAt}. Gitignored in both

## Deliberate design notes

- **One worker per /belmont:auto, NOT one worker per task.** §7.3's
  "two runtimes" framing could be read as "spawn a fresh runtime for
  every task" — that would be wasteful and trip the leak test by
  amplifying any per-construction handle creep 10×. Instead the
  worker survives the full auto run, with `runtime.newSession()` for
  each impl/verify phase. The 10-iter leak test asserts the exact
  contract: 10 worker constructions, 30 sessions (1 initial + 2 per
  worker), all disposed.
- **`unsubscribeCurrent()` BEFORE `runtime.newSession()`** in
  `worker.ts`. Pi's `runtime.newSession()` internally disposes the
  prior session, which clears all attached listeners pre-emptively
  (per `agent-session.d.ts`: "Remove all listeners and disconnect
  from agent"). If we called our Belmont-side unsubscriber AFTER
  that, the delete-from-Set returns false → unsubscribe count
  ≠ install count. Reordering keeps the 1:1 invariant true even when
  pi pre-clears listeners on dispose.
- **Stream every text_delta — but batch at message_end.** The user's
  M8 question chose "Stream every text_delta. Worker proxies all
  message_update events into Runtime A." We honour the spirit (no
  deltas dropped) but batch per assistant message — pi's `sendMessage`
  doesn't have an "update existing message" API, so 1 delta = 1
  sendMessage would create 1000 noisy entries per turn. The
  `WorkerEvent.text` carries `{content, partial}` — the loop's hook
  only emits when `partial === false`. M9+ can swap in a real
  streaming display path (e.g. `pi.registerMessageRenderer` updates
  in place) without changing the WorkerEvent shape.
- **AI fallback via the SAME worker — no second runtime.** §7.4 step
  2 ("structured decision via createAgentSession + customTools/noTools")
  could be a second pi entry point. We instead use the existing
  worker: `worker.newSession({model: nextTierModel}); promptCurrent(
  buildDecidePrompt(state))`; parse the assistant text for a JSON
  object. This keeps the leak test's contract (one worker, one
  dispose) and avoids a second pi/* file. Cost: one extra newSession
  per stuck-iteration — bounded by the §7.4 stuck-counter (3 max).
- **Path (b) for the leak test, not path (a).** pi 0.75.5 d.ts files
  do NOT expose `_internal.activeResources`. We use process-level
  active-handles + active-requests snapshots with ±2 slack. If a
  future pi exposes internal counters, the test's
  `snapshotProcessHandles()` helper swaps to path (a) without
  changing the assertion surface. The wrapper-internal counts
  (`runtimesCreated/Disposed`, `sessionsCreated/Disposed`,
  `subscribersInstalled/Unsubscribed`) are the part of the §8.4
  contract we CAN verify in v1.0 — file header documents this.
- **`.belmont/.gitignore` dogfooded at M8.** The init template ships
  one for fresh consumer projects (added at M3 with the scaffold);
  the source repo's own `.belmont/` previously relied on the root
  `.gitignore` for `.cache/` + `memory/steering/`. M8 lands `auto.json`
  + `auto.stop` which aren't in root `.gitignore`; mirroring the
  init template at `.belmont/.gitignore` keeps the policy
  self-documenting + safe.
- **`/belmont:steer` doesn't splice mid-turn.** D-008 ratified the
  consume-and-prepend grammar — steering is a "next iteration"
  signal, NOT a mid-pi-call interrupt. The user can `Ctrl+C` to abort
  the current pi child (which feeds `ctx.signal.abort()` per pi's
  standard contract); auto then halts at the next decide boundary
  and consumes any queued steering before the next sub-session
  prompt-build.
