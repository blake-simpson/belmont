# 2026-05-27 — M10 MCP bridge (in-house port)

## Buy-or-port verdict — PORT (defer pi-mcp-adapter to v1.1)

The M0 GO verdict at `spike/pi-mcp-adapter/VERDICT.md` listed three
re-evaluation triggers. M10 re-probed each at adoption time. **Same
risk-shape as pi-lean-ctx at M9** — the spike-time GO was based on
partial knowledge of the package's surface; closer inspection at
integration time revealed buy doesn't compose with Belmont's harness
extension model. Defer adoption; ship a minimal in-house layer that
covers only M10's needs.

### Trigger 1: pi-mcp-adapter major-version bump

- VERDICT.md baseline: 2.x.
- M10 state: still 2.x; latest `2.8.0` published 2026-05-25 (2 days
  before this session). 33 versions total since 2026-01-19; cadence is
  weekly. No major pivot. Description unchanged: "MCP (Model Context
  Protocol) adapter extension for Pi coding agent." ✅ unchanged.

### Trigger 2: `@modelcontextprotocol/sdk` major bump

- VERDICT.md baseline: 1.25.1.
- M10 state: upstream now at 1.29.0; pi-mcp-adapter 2.8.0 pins
  `^1.25.1`. Same major. ✅ unchanged.

### Trigger 3: pi base SDK major bump — **THE DISQUALIFIER**

- VERDICT.md baseline: `@earendil-works/pi-ai@^0.74`.
- M10 state: Belmont uses `@earendil-works/pi-{coding-agent,ai,tui}`
  pinned at `0.75.5`. pi-mcp-adapter 2.8.0 declares its peer deps as
  `@earendil-works/pi-ai@^0.74.0` and `@earendil-works/pi-tui@^0.74.0`.

  **The breaking detail:** `^0.74.0` in npm semver means
  `>=0.74.0 <0.75.0` — caret on a `0.x.y` version only allows patch
  bumps, NOT minor bumps. So pi-mcp-adapter 2.8.0 cannot install
  alongside our pi-ai/pi-tui 0.75.x without a `pnpm overrides` hack
  that would simultaneously break pi-coding-agent's own peer
  requirements.

  This alone is a hard adoption blocker until pi-mcp-adapter publishes
  a 2.9+ that widens the pi-ai/pi-tui peer to `^0.74.0 || ^0.75.0`
  (or equivalent). No such release as of 2026-05-27.

### Architectural mismatch the M0 VERDICT under-weighted

Equally important: pi-mcp-adapter is a **peer pi extension**, not an
embeddable library. The package.json carries `"pi": { "extensions":
["./index.ts"] }` and the README install path is `pi install
npm:pi-mcp-adapter`. There is no `main` or `exports` field at all —
the package ships raw `.ts` source loaded by pi's extension loader.

Consequences for Belmont:

1. **No Belmont-controlled config path.** The adapter reads its own
   files: `.mcp.json` (project), `~/.config/mcp/mcp.json` (user-
   global), `~/.pi/agent/mcp.json` and `.pi/mcp.json` (pi-owned
   overrides). The v2.3 §12.2 spec says `.belmont/mcp.json` — a
   different file. The adapter exposes no API to override the search
   path; the M0 VERDICT's `"@belmont/harness/src/mcp/index.ts —
   registers the adapter via pi's extension API; passes the project's
   .belmont/mcp.json through"` is not actually a thing the adapter
   supports.

2. **No insertion point for the auto:true gate.** pi-mcp-adapter
   directly calls `pi.registerTool()` from its own extension factory,
   outside Belmont's control. There is no middleware seam to inject
   the §12.3 blast-radius filter. Adding one would require forking
   the adapter (ongoing maintenance cost). The M0 VERDICT's
   "Belmont's blast-radius wrapper inspects `directTools` explicitly
   and refuses to register tools from servers not opted into auto"
   describes a wrapper that has no surface to insert at.

3. **Duplicate slash commands.** pi-mcp-adapter registers `/mcp`,
   `/mcp setup`, panels, an `mcp-setup-panel.ts` flow, and an
   `mcp({search, tool, args})` proxy tool. Belmont would coexist
   with — not control — that UI surface. The user would see TWO
   distinct mental models for MCP (Belmont's status + pi-mcp-
   adapter's panels) in the same REPL.

### Port scope deliberately deferred to v1.1

- OAuth (authorization_code, client_credentials, dynamic clients)
- StreamableHTTP → SSE fallback when server doesn't advertise SHTTP
- `directTools: true | string[]` (umbrella vs subset)
- `excludeTools` filter
- `exposeResources` (MCP resources surfaced as tools)
- User-global `~/.belmont/mcp.json` merge (v2.3 §12.2 mentions; §17
  M10 done-when doesn't require)
- The proxy `mcp({search, tool, args})` tool pattern from Mario's
  MCP-as-CLI essay. §17 M10 done-when calls for direct
  `mcp__<server>__<tool>` registration (per-tool surface, not
  umbrella). Proxy tool stays a v1.1 affordance once direct
  registration ships and stable.
- `keep-alive` lifecycle with health checks (we ship `lazy` + `eager`)

### Re-evaluation hook for v1.1

When pi-mcp-adapter publishes a release that:
1. Widens the pi-ai/pi-tui peer to `^0.75.0` AND
2. Exposes a programmable entry-point (not pi-extension-only) OR
3. Lets a host extension intercept its `registerTool` calls,

re-open this verdict. Until then, the in-house `mcp/*` is the §12
implementation.

## What landed

- **`packages/knowledge-schema/src/mcp-json.ts`** — `parseMcpJson(input)
  : { ok: true, data: McpConfig, warnings: Diagnostic[] } | { ok:
  false, diagnostics: Diagnostic[] }`. Strict on:
  - Transport ambiguity (BOTH `command` and `url` → reject).
  - Missing transport (NEITHER `command` nor `url` → reject).
  - Unknown `type` (only `"stdio"` and `"http"` accepted).
  - Server-name regex `[A-Za-z][A-Za-z0-9_-]*`.
  - Root shape `{ mcpServers: { ... } }`.

  Soft warnings (parse continues):
  - `auto:true + lifecycle:"lazy"` (the §12.3 invariant — auto loop's
    first `decide` may fire before lazy server connects).
  - Both `bearerToken` and `bearerTokenEnv` set (env-var wins).
  - `auth:"bearer"` without any token source.
  - Unknown server-level fields (forward-compat: v1.1 may add OAuth,
    directTools, etc.).

  19 tests in `packages/knowledge-schema/test/mcp-json.test.ts`.
  Re-exported from the package barrel (`McpConfig`, `McpServerConfig`,
  `McpStdioServer`, `McpHttpServer`, `ParseMcpJsonResult`,
  `parseMcpJson`).

- **`packages/harness/src/mcp/blast-radius.ts`** — `applyAutoModeFilter
  (config, isAutoMode)` is the load-bearing §12.3 safety primitive.
  When `isAutoMode === true`, drops every server missing `auto:true`
  from the returned config — NOT just "warns about", but literally
  filters them out before tool registration. The adapter's test asserts
  reachability directly (the fake McpClient for the filtered server is
  NEVER constructed), per the user prompt's explicit "test must assert
  reachability, not just config presence" requirement.

  Signal: `process.env.BELMONT_AUTO_MODE === "1"`. `auto/loop.ts` now
  sets the var at `runAuto` start and unsets it in the `finally` block
  (the same lockstep `try/finally` that disposes the worker — both
  guards against leak into subsequent interactive sessions).

  10 tests in `mcp-blast-radius.test.ts`.

- **`packages/harness/src/mcp/cache.ts`** — `.belmont/mcp-tools-cache.
  json` reader/writer. Schema version 1; readers ignore higher
  versions (forward-compat skip). Atomic tmp+rename mirrors
  `state/auto-json.ts`. Sources of cache invalidation:
  1. `sourceSha1` of `.belmont/mcp.json` differs from stored.
  2. `configHash` of the post-interpolation server config differs
     (catches `${VAR}` resolution changes even when mcp.json itself
     didn't move).
  3. Explicit `/belmont:mcp refresh` clears the cache.

  The cache filename was ALREADY in `init/templates.ts gitignoreTemplate
  ()` since M3 and in the dogfood `.belmont/.gitignore` — both shipped
  with `mcp-tools-cache.json` in anticipation. M10 didn't change those.

  10 tests in `mcp-cache.test.ts`.

- **`packages/harness/src/mcp/audit.ts`** — `recordMcpInvocation
  ({server, tool, autoMode, outcome, errorMessage?, durationMs?})`
  appends a bullet to today's `<date>-mcp-tools.md` episodic (kind
  `phase`, slug `mcp-tools`). Outcomes: `ok | error | refused-not-
  auto`. Long error messages truncate to 120 chars to keep bullets
  readable. `recordMcpServersForAutoRun(cwd, servers[])` patches
  `.belmont/auto.json#mcp` with the resolved (post-blast-radius)
  server descriptors — the v2.3 §12.4 "audit spine." No-op when
  auto.json is absent (interactive REPL path).

  `state/auto-json.ts` extended with `AutoJsonMcpEntry` type +
  `mcp?: AutoJsonMcpEntry[]` field + a `parseMcpEntries` round-trip
  helper. Backwards-compatible: existing auto.json files (no `mcp`
  field) parse fine; the field surfaces only when present.

  7 tests in `mcp-audit.test.ts`.

- **`packages/harness/src/mcp/transport.ts`** — `createMcpClient
  (server, env)` builds a connected-on-demand `McpClient` over
  `@modelcontextprotocol/sdk@1.29.0`. The `McpClient` interface is
  the public surface (`connect`, `listTools`, `callTool`, `close`).
  Production calls `new Client(...)` from the SDK + `StdioClient-
  Transport` or `StreamableHTTPClientTransport`. Tests inject a fake
  `McpClient` factory through `McpRegistryDeps.createClient` and
  exercise the full pipeline without subprocess spawn or HTTP.

  `${VAR}` / `$env:VAR` / `~/` expansion happens in `transport.ts` —
  exactly once per client construction — so the cache's `configHash`
  captures the resolved values and busts when env changes.

  **No pi-boundary change.** `@modelcontextprotocol/sdk` is NOT a pi-*
  package, so the B5 trust boundary (`.dependency-cruiser.cjs` +
  `test/pi-boundary.test.ts`) doesn't widen for M10. Same shape as
  the typebox dep added at M5: peer transport library, no boundary
  impact. Dep-check confirms: `77 modules / 164 dependencies cruised`
  (was 68/142 at M9).

- **`packages/harness/src/mcp/adapter.ts`** — the registry. Flow:
  1. Read `.belmont/mcp.json`; on ENOENT, return cleanly (no error).
  2. Parse via `parseMcpJson`; on hard failure, surface as
     `results: { "(mcp.json)": { kind: "failed", reason } }` and
     return — no exception bubbles up; the harness never crashes
     because of bad MCP config.
  3. Apply `applyAutoModeFilter` via the (injected) `isAutoMode()`
     probe. Non-auto:true servers are recorded as
     `{ kind: "skipped-no-auto" }` for the doctor surface.
  4. For each reachable server: hash the resolved config; check the
     cache; if hit, register tools from cache. If miss, spawn-probe
     (`client.connect()` + `client.listTools()`), populate cache,
     register. Lazy lifecycle servers disconnect immediately after
     probe; eager lifecycle keeps the connection.
  5. Each registered tool is named `mcp__<server>__<tool>`. The
     `execute()` impl audits every invocation (ok / error) and
     reconnects on demand if the client is closed.
  6. `recordMcpServersForAutoRun` patches `auto.json#mcp` only when
     running under auto (no-op for interactive REPL).

  Graceful degrade: per-server failure isolates to that server's
  `kind: "failed"` entry; the rest of the bridge stays up. §17 M10
  done-when "graceful-degrade on errors" satisfied.

  9 tests in `mcp-adapter.test.ts` (across the registration,
  blast-radius reachability, cache hit/miss/invalidate, parse-error,
  and audit-log paths).

- **`packages/harness/src/mcp/index.ts`** — single barrel for the
  whole MCP layer. Sibling modules reach in via `import { … } from
  "./mcp/index.js"` so the file layout under `mcp/` is internal.

- **`packages/harness/src/commands/mcp.ts`** — `/belmont:mcp` slash
  command. Two subcommands:
  - `doctor` (default) — READ-ONLY. Lists configured servers, their
    transport, auto-eligibility, lifecycle, cached tool counts,
    cache freshness vs mcp.json mtime, and any parser warnings.
  - `refresh` — clears the cache + re-runs `registerMcpServers`,
    which re-probes every reachable server.

  8 tests in `mcp-command.test.ts` cover the formatters end-to-end
  (no parse errors, missing mcp.json, fresh/stale/missing cache,
  excluded-in-auto, parser warnings, refresh summary).

- **`packages/harness/src/extension.ts`** — added `registerMcpCommand
  (pi)` next to the other slash commands, and a `try { await
  registerMcpServers(pi, ctx.cwd) }` block inside `session_start`
  after the M9 hooks. Failures notify-as-warning; the harness boots
  cleanly even when every MCP server fails.

- **`packages/harness/src/auto/loop.ts`** — single coupling point to
  the MCP layer: `process.env.BELMONT_AUTO_MODE = "1"` at the top of
  `runAuto`, `delete process.env.BELMONT_AUTO_MODE` in the `finally`
  block. No direct imports from `mcp/`. The signal flows ONE WAY
  (loop sets, adapter reads); the adapter never writes to the env.

## Deliberate design notes

### 1. No `directTools` / `excludeTools` filter modes in v1.0

The §17 M10 done-when says "All MCP tools register as
`mcp__<server>__<tool>`" — i.e. per-tool direct registration. v1.0
ships ONLY that mode. v1.1 may add the proxy `mcp({search, tool,
args})` pattern (per Mario's essay; mentioned in the M0 VERDICT but
NOT in v2.3 §12 itself — §12.5 does not exist in the canonical plan).

`directTools` and `excludeTools` server-level fields in mcp.json fall
through to the "unknown field" warning in the parser. v1.1 will
upgrade them to first-class.

### 2. No `--force` escape hatch for blast-radius

Per the user prompt's explicit "No --force escape hatch for the
blast-radius gate. v1.0 is strict: auto mode + non-auto:true server =
the server's tools don't exist as far as the worker is concerned."

The adapter's `mcp-adapter.test.ts` includes a reachability assertion
that the FAKE McpClient for a filtered server is NEVER constructed —
not just "the registered tool returns an error" — i.e. the gate is
applied BEFORE the client factory is called, not as a runtime check
inside the tool's execute() block.

### 3. `BELMONT_AUTO_MODE` is the single coupling point

The MCP layer has ZERO direct imports from `auto/loop.ts`. The loop
sets the env var; the MCP layer reads it. This keeps the bridge
testable in isolation (tests inject `isAutoMode: () => true`) and
matches how M9 wired `BELMONT_RTK_DISABLE` — env-var-as-signal is the
established Belmont pattern.

### 4. Cache hashes both `mcp.json` AND post-interpolation config

The `sourceSha1` invalidates the whole cache when mcp.json content
changes. The per-entry `configHash` additionally captures the resolved
(post-`${VAR}`) server shape — so a user who exports a new
`GITHUB_MCP_TOKEN` mid-session and runs `/belmont:mcp refresh` gets a
re-probe without having to touch mcp.json. Belt + braces.

### 5. `transport.ts` is the seam for v1.1

Everything that needs to swap when v1.1 ports back to pi-mcp-adapter
(OR layers in OAuth, OR adds SSE fallback) lives in `transport.ts`.
The `McpClient` interface — 4 methods, no SDK types leaked — IS the
extension point. The adapter never imports `@modelcontextprotocol/sdk`
directly.

### 6. ${VAR} interpolation supports BOTH POSIX and PowerShell shapes

`${TOKEN}` and `$env:TOKEN` both work, matching the Claude-flavoured
and pi-mcp-adapter-flavoured configs the user may already have. Same
interpolator across env, args, cwd, headers, bearerToken. Missing vars
resolve to empty string AND surface as a `missing[]` diagnostic — we
never fall through to a literal `${FOO}` in the expanded output
because that almost always papers over a real config bug.

### 7. `mcp_servers` BELMONT.md frontmatter field — NOT wired (Session 10 prompt was inaccurate)

The Session 10 prompt noted that "the `mcp_servers` field on BELMONT.md
frontmatter has been parsed since M2 but unused; M10 wires it." Grep
confirms this field does NOT exist in `ENTRYPOINT_SCHEMA` (frontmatter.
ts L76-79: only `schema` and `updated_at`). The source of truth for
MCP server config is `.belmont/mcp.json` at the project root, exactly
as v2.3 §12.2 specifies. No BELMONT.md changes needed for M10.
