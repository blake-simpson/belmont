# Skill Format & Per-Tool Wiring

**Domains:** cli, skills, agents

**Why this matters.** Belmont installs the same skill content for eight different AI CLIs. Before Phase 2 (April 2026) each CLI needed bespoke wiring — `.codex/belmont/` copies, `.cursor/rules/belmont/*.mdc` per-file symlinks, `.windsurf/rules/belmont` directory symlinks, `.gemini/rules/belmont` directory symlinks, `.copilot/belmont/` directory symlinks, plus `.claude/commands/belmont/` copies — and three of those targets were silently dead (the CLI didn't actually scan that path). The agentskills.io standard collapsed all of this into a single canonical location, `.agents/skills/<skill>/SKILL.md`, that every supported CLI auto-discovers natively. Phase 2 converged Belmont onto that layout.

## Invariant

- Skills live in `.agents/skills/belmont/<skill>/SKILL.md` with `name:` and `description:` YAML frontmatter (per agentskills.io spec).
- Each skill folder contains a `references/` subdir with the progressive-disclosure files that skill body actually references — only those, scoped per skill.
- Seven of eight supported CLIs (Codex, Cursor, Windsurf, Gemini, GitHub Copilot, Pi, opencode) auto-discover `.agents/skills/` natively. Belmont creates **zero per-tool wiring** for skill discovery for them.
- **opencode additionally gets generated per-skill wrapper commands at `.opencode/command/belmont/<skill>.md`** (registering as `/belmont/<skill>` — path-derived, `/`-namespaced) because its TUI `/` autocomplete lists commands only, never skills. These MUST be generated files, not SKILL.md symlinks — see Don't re-do.
- **Codex additionally gets generated per-skill UI metadata at `.agents/skills/belmont/<skill>/agents/openai.yaml`** carrying `interface.display_name: "belmont:<skill>"`. Codex's TUI `/` menu is built-ins only and NOT extensible (the `~/.codex/prompts` custom-prompt feature that could add slash entries was deprecated for skills, then removed upstream — gone by codex-cli 0.136); the grouped-autocomplete surface is the `$`-mention popup, which fuzzy-matches `interface.display_name` (preferred over frontmatter `name:` — `skill_display_name()` in codex-rs/tui). The shared `belmont:` prefix makes `$belmont` list every skill. Per agentskills.io the `agents/` subdir is product-specific config; the seven other CLIs ignore it, so it lives inside the canonical skill folders without breaking single-source. Display names >21 chars truncate visually in the popup (`belmont:working-backwards` → `belmont:working-back…`) but still match the full filter.
- **Claude Code uses per-skill slash-command symlinks at `.claude/commands/belmont/<skill>.md` → `../../../.agents/skills/belmont/<skill>/SKILL.md`.** Subfolders under `.claude/commands/` are namespace prefixes — `.claude/commands/belmont/implement.md` registers as `/belmont:implement`. The agentskills.io frontmatter on SKILL.md is also valid Claude Code slash-command frontmatter, so no rewriting is needed; references in the skill body resolve correctly through the symlink target's neighboring `references/` directory. The `.claude/agents/belmont` symlink is also written for parity but is not required for skill activation (Belmont's orchestrator skills dispatch agents inline via `subagent_type: "general-purpose"`, not as registered Claude Code subagents).
- Generated skill folders are NOT committed to git. Only `_src/` and `_partials/` are versioned. Generation runs on demand via `go generate`, on `belmont install --source` (auto-detects staleness), or in `build.sh` before `go build -tags embed`.
- **Conditional interactive-loop skills are gated by selected tool.** A skill listed in `conditionalSkills` (`cmd/belmont/main.go`) is authored, generated, and embedded like any other (`_src/<skill>.md` → `<skill>/SKILL.md`, also copied into the plugin), but the two skill-sync functions copy it into `.agents/skills/belmont/` only when the install publishes it. The map's value is the set of tools that can actually **run** the skill, and one table drives two decisions. The first member is `loop`, runnable by Claude Code (delegates to the built-in `/loop`) and Codex (starts Goal mode via `/goal`). Cursor, Windsurf, Gemini, GitHub Copilot, Pi, and opencode have no equivalent long-running interactive primitive.
  - **Shared surface** (`toolPublishesSkill`): a selected tool publishes the skill unless it has a private delivery path — Claude Code does, so a Claude-only install keeps `loop` off `.agents/skills/` and gets a **real** `.claude/commands/belmont/loop.md` file (content copied verbatim from the generated SKILL.md), not a symlink, because there is no `.agents/skills/belmont/loop/` target to point at. Codex publishes. If Codex is also selected, `loop` is on the shared surface and Claude gets the normal symlink.
  - **Per-tool command palette** (`skillRunnableByTool`, applied inside `syncSkillCommands`): a tool never gets a generated slash command for a skill it cannot run, *even when the skill is on the shared surface because a co-selected tool put it there*. Without this, a `--tools codex,opencode` install generates a first-class `/belmont/loop` for opencode — a dead end in the `/` palette, which is exactly the interactive regression this entry's first "Don't re-do" warns about. The skill's prose refusal is the last guard, not the first.
- **The shared surface is sticky for conditional skills; a machine's tool detection must never prune what another machine published.** `resolveSharedSurfaceSkills(skillsTarget, selectedTools)` runs once per `runInstall` and returns the publish decision per conditional skill: true when a selected tool publishes it **or when it is already installed in the target**. `.agents/skills/` is committed to git, but the tool selection is a property of the machine running the install — `belmont update` re-runs `install --no-prompt --tools all`, which `resolveTools` resolves to *detected* tools. Without stickiness a teammate (or CI) with no `codex` on PATH prunes `loop/`, `commitBelmontUpdate` commits the removal, and the next update from a Codex machine adds it back: the folder flaps in git forever. Dropping a published skill for good is a deliberate `rm -rf .agents/skills/belmont/<skill>` — nothing re-adds it unless a publishing tool is selected again. Stickiness cannot resurrect a legacy dead-end copy: `loop` was gated from the commit that introduced it, so no shipped version ever put it on the shared surface.

## How it's enforced

In `scripts/generate-skills.sh`:
- Walks `skills/belmont/_src/*.md`, expands `<!-- @include ... -->` partials into a temp file, then runs an awk frontmatter rewriter that injects `name: <filename>` after the opening `---` and drops any pre-existing `name:` line. Result lands at `skills/belmont/<skill>/SKILL.md`.
- For each generated SKILL.md, greps the body for `references/<X>.md` patterns and copies only those files from `_src/references/` into `<skill>/references/`. Robust to references that don't follow the `<skill>-` prefix convention (e.g. `models-yaml-format.md`, referenced from `tech-plan.md`'s body).
- Stale skill folders (target dirs with no matching `_src/` source) are pruned. Only directories that already contain a `SKILL.md` are touched, so user-created adjacent dirs are safe.

In `cmd/belmont/install_sync.go`:
- `//go:generate bash scripts/generate-skills.sh` directive (top of file) so `go generate ./...` regenerates.
- `ensureSkillsGenerated(sourceRoot)` runs in source-mode install before reading skills/. If any `_src/` or `_partials/` file mtime is newer than the matching SKILL.md (or no SKILL.md exists), it shells out to `bash scripts/generate-skills.sh`. Embedded mode is unaffected — embed.FS already contains the generated content.
- `syncSkillsFolderDir` (source mode) and `syncEmbeddedSkillsFolderDir` (embedded mode) sync `<skill>/SKILL.md` + per-skill `references/` from source/embed FS to `.agents/skills/belmont/`. Stale skill folders in target are removed.
- `setupTool` for cursor/windsurf/gemini/copilot/pi is a no-op for content (each prints `= .agents/skills/belmont auto-discovered`). For claude: keeps the `.claude/agents/belmont` directory symlink for sub-agent files, then `linkClaudeCommands` walks `.agents/skills/belmont/<skill>/SKILL.md` and writes one symlink per skill at `.claude/commands/belmont/<skill>.md`. For opencode: `linkOpencodeCommands` generates one wrapper command file per skill at `.opencode/command/belmont/<skill>.md` (frontmatter `description:` copied from the skill via `skillDescription`; body is the same "Run the belmont:X skill. Read .agents/skills/belmont/X/SKILL.md fully…" delegation that `adaptPromptForTool` uses, plus `$ARGUMENTS`), replacing any pre-existing symlink at that path *before* writing (writing through it would corrupt the canonical SKILL.md). Both share `syncSkillCommands`, which prunes stale `.md` entries (from removed/renamed skills) in the same pass. For codex: `writeCodexSkillInterfaces` generates `<skill>/agents/openai.yaml` per skill (idempotent content-compare; no prune pass needed — the file disappears with its skill folder when the skill sync removes a stale skill wholesale, and `syncSkillsFolderDir`/`syncEmbeddedSkillsFolderDir` never touch the `agents/` subdir so the metadata survives re-syncs).
- `runInstall` calls `resolveSharedSurfaceSkills(skillsTarget, selectedTools)` **once, before either sync path**, and threads the resulting `map[skill]bool` into `syncSkillsFolderDir` / `syncEmbeddedSkillsFolderDir` and into `collectOffSurfaceClaudeCommandsSource` / `collectOffSurfaceClaudeCommandsEmbedded`. One decision, four consumers — computing it twice is how the surface and the off-surface command file end up disagreeing (both a `loop/` folder and a real `loop.md` command, or neither). Each sync path asks `skillVisibleOnSharedSurface(name, sharedSurface)`; a skill that fails is `continue`d before being recorded in `sourceFolders`, so a copy the project no longer publishes is pruned by the stale pass.
- `offSurfaceClaudeCommandSkills` names conditional skills that Claude Code can still run while they are absent from `.agents/skills/`; `runInstall` builds a `name → SKILL.md content` map and threads it through `setupTool(projectRoot, tool, offSurfaceClaudeCmds)` → `linkClaudeCommands`. `syncSkillCommands` takes an `extra map[string]string` of off-surface commands: each is written as a real file and folded into the `wanted` set so the prune pass keeps it (opencode passes `nil`). It also takes the owning `tool` name and skips any skill failing `skillRunnableByTool` — so an unrunnable skill that IS on the shared surface gets no command and a stale one is pruned in the same pass. `ensureSymlink` replaces a regular file with a symlink (and `syncSkillCommands`' extra path replaces a symlink with a real file), so a project moves between the two Claude shapes cleanly when Codex is added or dropped.
- Unit coverage: `TestResolveSharedSurfaceSkills` (publish matrix incl. Claude-alone-does-not-publish and both stickiness cases), `TestLinkClaudeCommands_WritesOffSurfaceSkillAsRealFile` (real file not symlink, correct content, absent from `.agents/skills/`, survives re-run prune), `TestLinkClaudeCommands_LinksLoopWhenOnSharedSurface` (the symlink shape), `TestSyncSkillsFolderDir_HidesLoopWithoutCodex` (fresh install skips it), `TestSyncSkillsFolderDir_KeepsInstalledLoopWithoutCodex` (the update-flap regression — installed copy survives and is refreshed), `TestSyncSkillsFolderDir_InstallsLoopForCodex`, and `TestLinkOpencodeCommands_SkipsSkillsOpencodeCannotRun` (no `/belmont/loop` on a co-selected install; stale one pruned).
- `runLegacyCleanup(projectRoot)` runs once per `runInstall` (before `setupTool`), idempotently removing the dead Phase-2 / Phase-2.5 attempts at exposing skills to Claude Code (`.claude/skills/belmont`, `.claude/plugins/belmont`) plus all the per-tool wiring paths that no longer exist (`.codex/belmont`, `.cursor/rules/belmont`, `.windsurf/rules/belmont`, `.gemini/rules/belmont`, `.copilot/belmont`), plus stale `.agents/skills/belmont/*.md` flat files, stale `.agents/skills/belmont/references/` top-level dir, and `belmont:skill-routing` (or older `belmont:codex-skill-routing`) sections in `AGENTS.md` / `GEMINI.md`. `.claude/commands/belmont` is **not** in `legacyDirs` — that's the active install path.

In `.gitignore`: `skills/belmont/*/` excludes every generated skill folder, with `!skills/belmont/_src/` and `!skills/belmont/_partials/` overriding to keep sources tracked.

## Failure mode if you break it

- **Removing the agentskills.io frontmatter `name:` field**: skills become unindexed by Codex's `/skills`, Cursor's Skills panel, Gemini's `activate_skill` tool, and Windsurf's Cascade activation. Symptom: agent doesn't recognize `belmont:<skill>` references. Fix: re-run `generate-skills.sh` so the awk injector re-adds the field.
- **Reverting to flat `<name>.md` layout**: only Claude Code's legacy `.claude/commands/` would still see them. Codex/Cursor/Gemini/Windsurf/Copilot scan for `<dir>/SKILL.md`, not `<file>.md`. Symptom: silent zero-discovery for five of six CLIs.
- **Committing generated output**: drift between generated and committed becomes a recurring source of "did you regenerate?" footguns. Phase 1 had this exact problem with the flat layout — every partial change required two commits (source + generated). Don't reintroduce it.
- **Per-skill references lost or wrong**: skill body says `references/foo.md` but the file isn't in `<skill>/references/`. Symptom: agent reports "file not found" mid-skill. The grep + copy in `generate-skills.sh` solves this; `generate-plugin.sh`'s old `*-prefix glob` did NOT (it missed `models-yaml-format.md` for tech-plan). Don't go back to prefix globs.
- **Skipping `runLegacyCleanup` after upgrade**: users who came from Phase 1 keep stale `.codex/belmont/` and `belmont:skill-routing` sections in AGENTS.md/GEMINI.md indefinitely. Symptom: confused users seeing "ghost" Belmont content in their AGENTS.md they didn't write. Cleanup is idempotent and runs every install — keep it.
- **Detect-tools regression**: if `detectTools` only checks dir presence (the pre-Phase-1 default), upgrades from Phase 1 silently drop Codex/Copilot/Gemini wiring (those tools never created marker dirs). The fix is the three-signal detection: dir presence OR PATH binary OR existing routing marker in AGENTS.md/GEMINI.md.

## Don't re-do

- **Install Claude Code skills as `.claude/skills/<namespace>/<skill>/SKILL.md`** (nested-namespace folder). Claude Code's project-level skill discovery at `.claude/skills/` is **single-level only** — it scans `.claude/skills/<skill>/SKILL.md` and ignores everything below the first level. The April-30 restructure read `code.claude.com/docs/en/skills` as supporting nested namespaces and shipped 0.10.3 with `.claude/skills/belmont/<skill>/SKILL.md`. Result: zero `belmont:*` entries in `claude -p`'s init message, every Belmont auto-loop iteration was a no-op (claude received "use the implement skill" prompts but had no such skill registered, glob-and-exit in 2-3s).
- **Install Claude Code skills as a project-local plugin at `.claude/plugins/belmont/.claude-plugin/plugin.json`.** Tempting because plugins are how `figma:*`, `vercel:*`, `verona:*` namespaces work in the user's session — and the docs *do* show the manifest format. Cost: project-local plugins are **not auto-discovered** by Claude Code 2.1.x. They require either (a) the `--plugin-dir` CLI flag (per-session, not what users want for slash commands), (b) marketplace registration in `settings.json` `extraKnownMarketplaces` followed by interactive `/plugin install`, or (c) being installed from a public marketplace. None of those work for a zero-friction `belmont install`. Verified empirically: writing `.claude/plugins/belmont/` with a valid manifest and a `skills/` symlink produced zero `belmont:*` entries in `claude -p`'s init `plugins`/`skills`/`slash_commands` lists.
- **Drop the `belmont:` namespace and install flat symlinks at `.claude/skills/<skill>/`** (no namespace prefix). Tempting as the simplest single-level fix, but skill names like `implement`, `verify`, `next`, `status`, `cleanup`, `debug` collide with Claude Code's built-in slash commands (`/debug`, `/init`, `/review`, `/security-review`, etc.) and with other plugins' generically-named skills. The `belmont:` prefix is load-bearing.

**The right answer is `.claude/commands/belmont/<skill>.md`** — Claude Code's slash-command discovery scans `.claude/commands/`, treats subfolders as namespace prefixes (so `commands/belmont/implement.md` registers as `/belmont:implement`), and accepts the agentskills.io frontmatter as-is. This is what Belmont 0.9.x and earlier shipped, what the April-30 restructure replaced, and what 2026-05-07 restored after the two failed alternatives above.

**Verify any future "skills layout" change against `claude -p ... --output-format stream-json --verbose` init output before shipping.** If the `skills` / `slash_commands` / `plugins` lists don't include `belmont:*`, the layout is wrong — no amount of correctness in the file structure compensates for not being discovered.

- **Symlink SKILL.md as opencode command files** (the Claude Code trick, at `.opencode/command/belmont/<skill>.md` → SKILL.md). Tempting for single-source parity, and the files DO load — but they register under the WRONG name. opencode's command loader (`packages/opencode/src/config/command.ts`) builds the raw config as `{name, ...md.data, template}`: the frontmatter spread comes *after* the path-derived name, so SKILL.md's mandatory agentskills.io `name:` key overrides `belmont/<skill>` and the command registers as bare `implement`/`status`/etc. Net effect: nothing under `/belmont` in the TUI ("No matching items"), and the bare-named command shadows the same-named skill in opencode's command registry (skill-sourced commands are only added `if (!commands[item.name])`). Verified empirically on opencode 1.15.13 (2026-06-03): a symlinked SKILL.md with `name: world` registered as `world`, not `belmont/world`; a regular file without `name:` registered correctly as `belmont/hello`. The wrapper-file approach (no `name:` key, description-only frontmatter, delegation body) is the fix; it also sidesteps the relative `references/` path problem a raw SKILL.md body would have when executed as a command template from the project root.
- **Expose Belmont in Codex's `/` slash menu** (via `~/.codex/prompts/belmont-*.md` custom prompts or any per-project equivalent). Custom prompts were global-only (never per-project), flat (subdirs ignored, no namespacing), officially deprecated in favor of skills, and then removed from the codebase entirely — `codex-cli 0.136` no longer reads `~/.codex/prompts` at all, and the TUI's `command_popup.rs` builds exclusively from hardcoded built-ins. There is no extension point; Codex plugins ship skills/MCP/hooks, not slash commands. The supported grouped-autocomplete surface is the `$`-mention popup driven by `interface.display_name` — that's what `writeCodexSkillInterfaces` targets.
- **Restructure source `_src/` to a folder layout** so it matches the output 1:1. Tempting because it's "cleaner". Cost: every skill becomes a directory, harder to scan in `ls _src/`, more boilerplate when adding/renaming, and the actual content is still a single markdown file per skill. Flat sources + folder generation is the better tradeoff.
- **Per-CLI install wiring** that copies content into `.codex/`, `.gemini/rules/`, `.copilot/`, etc. The agentskills.io standard means every supported CLI reads `.agents/skills/`. Adding per-tool dirs is dead writes that confuse users (they see Belmont files in places the tool doesn't actually look).
- **Strip the `<skill>-` prefix from reference filenames** (so `implement-milestone-template.md` becomes `milestone-template.md` inside `implement/references/`). Tempting because the prefix is redundant. Cost: skill body path-rewriting required, brittle. Keep the prefixed naming — paths in skill bodies resolve correctly without rewrites.
- **Use a top-level shared `references/` dir** (`skills/belmont/references/<topic>.md`) instead of per-skill folders. Was Phase 1's layout. Cost: skill body relative paths resolve to the wrong location once the skill itself moves into a subfolder; plus references are loaded for every skill regardless of need. Per-skill folders give precise progressive disclosure.
- **Keep AGENTS.md / GEMINI.md routing sections** "as a fallback for new CLIs that don't auto-discover". Costs ~10 lines in user-owned files for ambiguous benefit. Every supported CLI as of April 2026 auto-discovers `.agents/skills/`. If a future CLI doesn't, add wiring then; don't pollute every project preemptively.
- **Skip `--bare` / hermetic-mode flags** when adding new tools. The bare-mode pattern (Claude's `--bare`, Codex's `--ignore-user-config`, Gemini's `--skip-trust`) is the right way to make scripted runs deterministic. Belmont doesn't use these today but should add them when porting the auto loop to a CI environment.

- **Make a conditional skill "conditional" by content alone** (ship it on the shared `.agents/skills/` surface and have its body say "STOP if you are not the right tool"). Tempting because it needs zero Go changes. Cost: the skill still appears in every other CLI's skill list and `$`/`/` autocomplete, so a Cursor/opencode/Pi user can invoke it and gets a dead-end refusal — exactly the interactive-side regression the dual-path rule warns against. The hard gate (`conditionalSkills` + selected-tool filtering + per-tool command filtering + off-surface Claude real command file) keeps it hidden for installs that cannot run it. Codex is the exception for `loop` because `/goal` is now the matching primitive.
- **Gate the shared surface but not the per-tool command palettes.** The two filters look redundant on a single-tool install and are not: `.agents/skills/` is one directory shared by all eight CLIs, so *any* publishing tool in the selection makes the skill visible to *every* co-selected tool's command generator. Gating only the surface hands opencode a `/belmont/loop` on a `codex,opencode` install — the dead-end refusal above, arrived at from the other direction.
- **Decide shared-surface visibility from the selected tools alone.** `belmont update` re-runs `install --no-prompt --tools all` → `resolveTools` → *detected* tools, which is a property of the machine, not the project. A pure-selection rule prunes a published `loop/` on any teammate or CI box without `codex` on PATH, `commitBelmontUpdate` commits the deletion, and the next update from a Codex machine restores it — the folder flaps in git forever, and the two states are indistinguishable from an intentional change in review. `resolveSharedSurfaceSkills` reads the installed state first for exactly this reason. Persisting the selection to a new state file was the alternative; it needs a new file, a migration for projects that predate it, and an answer for "explicit `--tools` disagrees with the persisted set" — the installed folder already carries the same information.
- **Write an off-surface Claude command as a symlink into `.agents/skills/belmont/<skill>/SKILL.md`** like the normal Claude commands. Can't when the skill is NOT synced there, so the symlink target doesn't exist. It must be a real file whose content is read from the source/embed generated SKILL.md at install time. `syncSkillCommands`' `extra` map carries that content; a pre-existing symlink at the path (from an older install where the skill *was* on the shared surface) is removed before the real file is written, mirroring the opencode wrapper's symlink-replacement guard.

## Evidence

- Verified against live docs (April–May 2026) for all six CLIs:
  - Cursor: cursor.com/docs/context/skills lists `.agents/skills/` among workspace skill dirs.
  - Gemini: geminicli.com/docs/cli/skills/ confirms `.agents/skills/` is the documented `.gemini/skills/` alias and "takes precedence" over `.gemini/skills/`.
  - Codex: codex-rs/core-skills/loader.rs constants `SKILLS_FILENAME = "SKILL.md"` and `AGENTS_DIR_NAME = ".agents"`.
  - Windsurf: docs.windsurf.com/windsurf/cascade/skills says `.agents/skills/` is auto-discovered alongside `.windsurf/skills/`.
  - Copilot: docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills lists `.agents/skills` among the project-scope scan paths.
  - Claude Code: code.claude.com/docs/en/slash-commands documents `.claude/commands/<name>.md` (and subfolders as namespaces — `.claude/commands/group/x.md` → `/group:x`) as the slash-command location. Skills at `.claude/skills/<skill>/SKILL.md` are also supported but discovery is single-level. Plugins at `.claude/plugins/<name>/` are NOT auto-loaded — they require `--plugin-dir`, `extraKnownMarketplaces`, or marketplace install.
- The April-30 restructure (commit `3e10843`) misread the Claude Code skills doc as supporting `.claude/skills/<namespace>/<skill>/SKILL.md` and shipped that layout in 0.10.3. Verified broken on 2026-05-07 with Claude Code 2.1.132: `claude -p ... --output-format stream-json --verbose`'s init message showed zero `belmont:*` entries in either `skills` or `slash_commands` while plugin-loaded skills (`vercel:*`, `figma:*`, `verona:*`) appeared correctly. A second attempt the same day to install as a project-local plugin at `.claude/plugins/belmont/.claude-plugin/plugin.json` ALSO produced zero entries — project-local plugins aren't auto-discovered. The 2026-05-07 fix restored the pre-restructure `.claude/commands/belmont/<skill>.md` layout, with per-skill symlinks pointing at the canonical `.agents/skills/belmont/<skill>/SKILL.md` so the agentskills.io content stays single-source.
- Unit coverage: `cmd/belmont/commit_update_test.go` includes `TestRunLegacyCleanup_RemovesLegacyDirsAndAgentsSection` (now also asserts `.claude/skills/belmont` and `.claude/plugins/belmont` are removed on upgrade), `TestRunLegacyCleanup_Idempotent`, `TestCommitBelmontUpdate_StagesDeletionOfLegacyPath`, `TestLinkClaudeCommands_SymlinksPerSkill`, `TestLinkClaudeCommands_PrunesStaleEntries`, `TestLinkOpencodeCommands_GeneratesWrapperPerSkill` (asserts regular file, no `name:` key, description + delegation body + `$ARGUMENTS`, idempotency), `TestLinkOpencodeCommands_ReplacesLegacySymlink` (asserts SKILL.md isn't corrupted by writing through a pre-existing symlink), and `TestLinkOpencodeCommands_PrunesStaleEntries`.
