# `[!]` Is a Decision Queue, Not a Failure

**Domains:** skills, cli, state, auto-mode

**Why this matters.** `[!]` is the only marker in Belmont's set that usually means the work is waiting on a person. Every other state describes work an agent can move: `[ ]` can be built, `[x]` can be verified, `[-]` is already settled. A `[!]` normally means the missing input is a human — an approval, a product or architecture ruling, a credential, a console action nobody automated, a spec change that belongs to `/belmont:tech-plan`. *Usually*, not always: two writers mint a `[!]` whose reopen condition an agent can check (see the Invariant below), and conflating the two is its own failure.

The state model protects it unevenly, and the uneven part matters. `mergeProgressState` refuses to rank over `[!]` from either direction. `resolveProgressConflict` agrees with it since #46 — `[!]` wins from either direction there too, and whichever side's decision wins, the state it displaced is named on stderr. Before that it short-circuited the rank comparison but kept *ours*, so a blocker the incoming side raised was discarded whenever this side held a more advanced state, and which of the two rules applied depended only on whether git happened to register a conflict. (A blocker the incoming side has and ours does not stopped being dropped at #43, which gave that function a carry.) `skipMilestoneInProgress` used to rewrite `[!]` to `[x]` outright — its regex was `[ >!]`, so skipping a milestone laundered its unanswered questions into done. Since #40 the regex is `[ >]`, `[!]` is left alone, and a milestone whose only remaining work is blocked fails the skip rather than reporting success. And the reconciliation agent is instructed to clear a `[!]` when the other side of a merge is `[x]`/`[v]`. So "Belmont never overwrites a `[!]`" is false as a blanket claim; what is true is that the *merge of two PROGRESS.md files* preserves it. Either way, protecting a signal is not the same as surfacing it, and *nothing decided what a running loop should do when it hits one*. Two opposite failures followed from that gap, and both were observed on the same feature.

**Failure one: the loop treats a blocker as a stall and stops.** A `[!]` in M1 stops a feature whose M2–M17 have nothing to do with it. On the observed feature that would have stranded 16 milestones behind one product question.

**Failure two: the loop treats a blocker as a bug and grinds at it.** A human-gated follow-up classified as *blocking* burns fix rounds that cannot succeed, then trips the circuit breaker, which defers everything remaining — so the security item that needed a password rotation lands in a polish bucket. Attempting it harder is the one thing guaranteed not to work.

Underneath both: **the queue was never legible.** The observed feature banked 19 blocked follow-ups over one overnight run, every one a question for the same person. `belmont status` did list each of their checkbox lines in full, in both views — what it never showed was the **indented body**, which is where the question actually lives, and it never grouped the queue across features or separated it from the progress counts it was interleaved with. 87 tasks verified, 0 of 17 milestones readable as done, and no single surface that said what the person actually had to answer.

## Invariant

- **Scope: these describe `/belmont:loop`.** `belmont auto` deliberately does the opposite — `decideLoopAction` Rule 1 (`auto_decide.go:14`) PAUSEs the whole feature on the first `[!]`, and `checkHardGuardrails` repeats the check. That is the right headless answer: nobody is watching, so an unanswered question must reach a person before anything else runs. Do not read the invariants below as path-agnostic. Changing auto is a behaviour change needing its own eval, and is not attempted here.
- **In `/belmont:loop`, a `[!]` never stops the loop by itself.** Step 0 of the recipe selects past a milestone whose only live work is `[!]`, to the next one holding a `[ ]`, `[>]` or `[x]`. It stops for the user only when *every* remaining pending task in the feature is `[!]` — at that point no agent action can change the file.
- **No skill clears, answers, or converts a HUMAN-GATED `[!]`.** Not to `[-]` to make a milestone read complete, not to `[ ]` to retry it, not to `[v]` because the surrounding work passed. Writing one is allowed; clearing one is the user's.
- **Two `[!]` writers are not human-gated, and carry a checkable reopen condition.** `_partials/milestone-immutability.md` mints a `[!]` for work blocked on a later milestone `M<N+k>`, reopened as `[ ]` once `M<N+k>` verifies; `agents/belmont/reconciliation-agent.md` clears one when the other side of a merge is `[x]`/`[v]`. The reason line on the task is what distinguishes them from a question for a person — which is what the reason is for. Any text that states the prohibition must carve these out, or it contradicts a partial the same skills `@include`.
- **Human-gated is classified before blocking, not after.** The test is not difficulty or severity — it is whether the missing thing is a *person*. A security item or an unmet acceptance criterion that needs an approval is human-gated, not blocking. Getting the order wrong is failure two.
- **A human-gated task is not a fix round.** An attempt that cannot succeed must not count toward the circuit breaker, or two of them defer the real work.
- **The circuit breaker never sweeps `[!]`.** It defers what is still classified *blocking*.
- **A milestone is left only when every task in it reads `[v]`, `[-]` or `[!]`.** Never `[ ]`, `[>]` or `[x]`. This is the rule that stops follow-ups accumulating, and its absence is visible in the evidence below: 92 of 165 task lines were verification-generated follow-ups, most of them `[ ]` in milestones the loop had already left, because nothing required a milestone to be *settled* before moving on. An `[x]` the final verify will not promote becomes `[!]` — an agent tried and could not clear it, which is a question, not a leftover that reads as done. Settling is safe because `[-]` and `[!]` are both reversible by the user and both visible in `belmont blockers`; a `[ ]` left behind is the unsafe state, because it looks like scheduled work and is nobody's decision.
- **The fix-round count is per milestone PER SESSION,** and starts at zero each run. A session beginning after the user has answered decisions or reopened work carries a fresh mandate; inheriting the previous run's count would defer the very work they just asked for. The durable per-milestone history is `MILESTONE-<M>.done.md` — one `# Milestone:` heading per pass — which the append rule guarantees and which survives compaction better than the `## Loop decisions` ledger. Earlier text claimed the ledger was the only record; it never was.
- **Bounding a milestone is not ending the run.** A task left at `[x]`, a fired circuit breaker and a `[!]` all bound the *milestone* they occur in and all three make the run's final verdict INCOMPLETE — but none of them halts the loop. Step 5 keeps "do I continue" and "what do I report" as separate questions on purpose: an earlier draft made the breaker a session stop, and on a real run that ended a 17-milestone feature at M6 with five pending follow-ups in M7 and twenty-eight tasks in M11-M17 untouched. That is the same stranding the `[!]` rule two bullets up exists to prevent, reintroduced under a different name. If you add a fourth condition of this shape, add it to the verdict, not to the stop list.
- **The queue is reportable in one command.** `belmont blockers` prints every `[!]` Belmont can find across every feature — inside milestones, and, reported separately, on task lines outside every milestone, which are invisible to `parseMilestones` and therefore to every count. It never prints an all-clear about a file it could not fully read.

## How it's enforced

Mechanically (cannot be dropped by an agent):

- `belmont blockers` (`cmd/belmont/blockers.go`) — `buildBlockers` walks every feature (or one) and pulls each blocked task's indented body with `taskDetail`, which extends `taskBodyEnd` by also stopping at a sibling checkbox line (under a nested list `taskBodyEnd` alone would swallow every following task into the first one's body). It reads live state the two ways `buildStatus` does: `loadAutoWorktreeStateByMilestone` + `overlayLiveMilestones` for single-feature-parallel runs, falling back to `loadAutoWorktrees` otherwise. Using `loadAutoWorktrees` alone was wrong and shipped briefly — it collapses a per-milestone worktree map to one representative directory, so a `[!]` raised in any other milestone's worktree was invisible here while `status` showed it and pointed the reader at this command. Each entry carries the **path** of the file its line number belongs to, because during a run that file is inside a worktree and master's line numbers differ. Reports only; it has no write path, because a command that both raises a question and resolves it is free to guess the answer.
- `renderStatus` names it after the blocked list in the `--feature` detail view.
- **Known gap, not fixed here: the multi-feature listing reads the wrong worktree in single-feature-parallel mode.** `listFeaturesWithOverrides` gets its milestones through `loadAutoWorktrees`, the same collapse `buildBlockers` had to abandon — so with worktrees for M1 and M2 and a `[!]` only in M2's, the listing shows no Blocked section at all while `--feature` and `belmont blockers` both show it. The collapse is pre-existing; what is new is that the listing now carries a pointer *to* `blockers`, so the two surfaces can disagree. Fixing it means plumbing the per-milestone map into the listing path and is its own change. Until then, treat the listing's blocker section as advisory during a parallel run and trust `belmont blockers`.
- `renderFeatureListing` caps blockers at `blockedListingCap` (3) per feature and prints the withheld count plus the exact command. The listing is the whole-project overview; one feature's 19-item queue used to bury every other feature. Nothing is hidden — the count and the command print on the next line, and the detail view still lists every one.
- `mergeProgressState` / `canonicalMarker` already refuse to rank over `[!]`; see [`progress-md-parsing.md`](progress-md-parsing.md).
- Tests in `cmd/belmont/blockers_test.go`: `[-]` never enters the queue; a blocker with no body does not borrow the next task's lines; an **indented** sibling task is not swallowed; both live-run shapes (per-milestone worktrees, and a half-cleaned override falling back to master); orphaned blockers; `--summary` really being one line per blocker; and the `renderStatus` pointer line, which nothing asserted.

By prose (reduces the chance of the failure, cannot prevent it):

- `_src/loop.md` — a step **0** that picks the target milestone before dispatch, because nothing else does: `nextMilestone` (state.go) returns the first milestone that is not all-done with its `(depends: …)` met (#59), and `implement.md` Step 1 selects the first *eligible* pending milestone — and a `[!]` satisfies both forever. Without step 0 the rule "move past it" has no mechanism and the loop re-targets the blocked milestone every iteration. Step 0 also classifies **who executes** the milestone before dispatching at it (#58): work the spec assigns to a person — an interactive fixture run, a sign-off, a console action — is triage's human-gated class known in advance, marked `[!]` with its reason at selection time rather than after an implementation agent has failed or fabricated against it. That is what makes the all-`[!]` stop reachable on a feature whose tail is human-executed. Plus triage's three-class split with human-gated checked first, the `[!]`-does-not-stop rule, the `belmont blockers` handoff, the user-steering stop, and the `<range>` bound (`/belmont:loop <feature> --from M<a> --to M<b>`, #58) that scopes selection, every stop condition and the verdict — all **inside the fenced recipe**, which is the only text guaranteed to survive compaction.
- `_src/implement.md` Step 1 rule 0 — honour an explicitly named milestone instead of re-deriving it. Step 0 above is inert without this.
- `_src/implement.md` and `_src/next.md` both **append** to `MILESTONE-<ID>.done.md` when one exists. Two files owned this rule and a review caught only one of them: `next.md` said "overwrite it" and `implement.md` said "archive by renaming it", which replaces the target just as silently. The archive is keyed on the milestone while both skills can run against the same milestone repeatedly — a re-entered milestone, a reopened follow-up, a batch that already archived there. On the run that exposed this, one milestone's archive held four passes and 118KB; a single re-entry under the old rule would have left one.
- `prompts/belmont/post-verify-triage.md` — the **auto**-path counterpart. Same three-class split, and the same `[-]`-not-deletion rule. This is the path where `mergeProgressState` actually runs, so the deletion bug was worse here than in the interactive skill; per AGENTS.md's dual-invocation rule, converting one without the other is the half-converted set that entry warns about.

## Failure mode if you break it

- Classify human-gated as blocking → two dead fix rounds per milestone, then the circuit breaker defers a real issue as polish.
- Stop the loop on the first `[!]` → every independent milestone behind it is stranded, and the run reports a stall rather than a question.
- Let an agent clear a `[!]` to make a milestone read complete → the feature computes Verified over work nobody approved. This is the `[v]`-without-evidence failure ([`verified-flip-recording.md`](verified-flip-recording.md)) with a different marker and no guard, because no Go code audits a `[!]` that disappeared.
- Leave the queue visible only in `belmont status` → the checkbox lines are there but the bodies are not, so the questions are read one headline at a time in the middle of a report about something else, and go unanswered for as long as the run lasts.
- Report a blocker's line number without its path → during an active run that number belongs to a worktree copy, and the reader opens master's file at a line that is a different task or past EOF. Worse, an answer written into master during a run is overwritten by `mergeProgressState` on merge, so the one thing this feature exists to protect is silently lost.

## Don't re-do

- **"Add an `[a]` awaiting-approval marker."** Rejected. `[!]` already means exactly this, every reader already handles it, and adding a marker changes the meaning of files already in the wild — the expensive lesson from `[-]` and `[V]` (see [`progress-md-parsing.md`](progress-md-parsing.md)). The gap was never the marker; it was that nothing surfaced or routed around it.
- **"Let the loop ask the user inline and continue."** Rejected for the delegated `/loop` path. The loop's premise is that it runs unattended across compaction; a question asked into a transcript nobody is watching is worse than a queue, because it leaves no record on disk.
- **"Have `belmont blockers` clear a task once answered."** Rejected. The answer arrives as prose from a person; encoding it means guessing which task it settles. Editing the marker by hand, or letting `/belmont:next` pick the task up once the input exists, keeps the human in the one loop that needs them.
- **"Exclude blocked milestones from the feature's milestone count so it can read Complete."** Rejected. A milestone holding an unanswered question is not done, and `[-]` already exists for work genuinely dropped. Withdraw it deliberately or answer it.
- **"Put the blocked-stop rule in the skill's `## Stop conditions` prose."** Rejected — that is where it was, and it is the section most likely to be summarised away mid-run. Every stop condition lives inside the fenced recipe handed to `/loop`, which is the only text guaranteed to travel with the delegated task. The prose section restates them for a reader.

## Evidence

A large PM-tooling feature, overnight run on Belmont 0.10.17. Snapshot mid-run: **165 task lines, of which 92 were verification-generated follow-ups** — more than half the feature's total work was created by its own verification passes. Marker breakdown 87 `[v]` + 9 `[x]` + 50 `[ ]` + **19 `[!]`** = 165. The blocked tasks were spread across ten of the seventeen milestones, every one of which therefore computed as "has blockers", so the feature read `0/17 milestones done` against 87 verified tasks. The nineteen were shaped like: an apply awaiting sign-off, an operator action nobody automated, a credential rotation, a product ruling on a default, and a decision about whether a signal should propagate to another subsystem. None is a bug; none can be closed by an agent; all nineteen were visible only as headline task lines at the bottom of `belmont status`, which never showed the indented body where each question actually lives.
